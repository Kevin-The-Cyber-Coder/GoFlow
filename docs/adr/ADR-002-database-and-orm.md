# ADR-002: PostgreSQL, Drizzle ORM and versioned SQL migrations

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** Project maintainer

## Context

GoFlow stores financial records. The data model is relational by nature: clients
own invoices, invoices own line items, payments reference invoices, and every
record belongs to a workspace. Correctness depends on constraints, not on
application code remembering to check.

Financial operations also need transactions with row-level locking: recording a
payment must recompute an invoice balance without two concurrent payments
overwriting each other.

## Decision

- **PostgreSQL 17** as the database.
- **Drizzle ORM** for typed queries and schema definition.
- **SQL migration files committed to the repository**, generated by
  `drizzle-kit generate` and reviewed by hand before merge.
- Migrations live in `apps/api/src/db/migrations` — next to the schema they
  describe, with no copy step between generation and deployment.

## Alternatives considered

**Prisma.** Excellent developer experience and tooling, but the query engine adds
a runtime layer and generated-client step, and expressing row-level locks or
partial indexes falls back to raw SQL anyway. For a project where the financial
queries are the point, closer-to-SQL wins.

**Raw `pg` with hand-written SQL.** Maximum control, but no compile-time type
safety for row shapes and a large amount of mapping boilerplate. Drizzle is
effectively typed SQL with a schema definition attached.

**MongoDB or another document store.** Financial data is highly relational and
needs cross-record invariants (a payment cannot reference an invoice in another
workspace). Enforcing that in application code is strictly worse than a foreign
key.

## Consequences

- Constraints, foreign keys and indexes are expressed in the schema and enforced
  by the database, not by convention.
- Migrations are reviewable SQL in the diff, which is the right level of scrutiny
  for schema changes on financial data.
- Drizzle's API changes between minor versions more than Prisma's; upgrades need
  attention.
- No `drizzle-kit push` in any shared environment — schema changes only ever
  arrive through a reviewed migration.

## Implementation notes

- Timestamps are `timestamptz`, stored in UTC.
- Money columns are `bigint` minor units with a separate `char(3)` currency code
  (see [ADR-003](ADR-003-money-representation.md)).
- Multi-row financial writes run inside `db.transaction(...)` and lock the parent
  invoice row with `SELECT ... FOR UPDATE` before recomputing balances.
- The local Postgres container applies `docker/postgres/init/01-extensions.sql`
  on first start, which enables `citext` for case-insensitive email uniqueness.
